# Notebooks, Reports and Publishing

The habit to build: **a report is a product the pipeline regenerates**, not a
document you edit by hand. When the data updates, `doit` rebuilds every
exhibit, number, notebook and page.

## Notebooks: jupytext percent format
Notebooks are useful for literate exposition (code + output + prose). They are
also hard to diff, easy to run out of order, and poor at long jobs. The course
fix:

- **Author `src/NN_topic.ipynb.py`** (jupytext percent format), not `.ipynb`.
  The `.py` is what git tracks and diffs.
- **The DAG executes them.** `jupytext --to notebook` → `nbconvert --execute`
  → HTML into `_output/`. Executed `.ipynb` files are build products and are
  gitignored.
- **Notebooks tour and explain. Modules compute.** Import `calc_*`/`load_*`
  functions. If a notebook cell grows reusable logic, move it into a module and
  test it there.

Format rules:
```python
# ---
# jupyter:
#   jupytext:
#     text_representation:
#       extension: .py
#       format_name: percent
#       format_version: '1.3'
#       jupytext_version: 1.18.1
#   kernelspec:
#     display_name: Python 3
#     language: python
#     name: python3
# ---

# %% [markdown]
# # 01. Yield Curve Tour
#
# Every markdown line starts with "# ". A bare "#" is a blank line.

# %%
import pull_fed_yield_curve
from settings import config

OUTPUT_DIR = config("OUTPUT_DIR")

# %%
df = pull_fed_yield_curve.load_fed_yield_curve()
df.tail()
```
- Use `# %% [markdown]` + `# `-prefixed lines for prose. Do not use triple-quoted strings.
- End a cell with a bare expression (`df`, `fig`) to display it, rather than `print(df)`.
- Use `.glimpse()` for wide Polars frames.
- **No `sys.path.insert` and no `__file__`**, because neither works once the file is
  converted. The DAG runs notebooks from `src/`, so imports resolve.
- No defensive checks for missing files or empty frames. The DAG guarantees inputs.
- Register each notebook in `dodo.py` (`notebook_tasks`) with every module and
  data file it reads as `file_dep`, and every file it writes as `targets`.

## Exhibits: tables, charts and numbers generated by code
- **Tables** are written with `DataFrame.to_latex(...)` (or `Styler.to_latex`)
  to `_output/<name>.tex`, column-only `tabular` environments. The report
  wraps each in `table`, `caption` and `label`. Escape `%` and `_` in labels.
- **Charts** are written to `_output/` as `.png`/`.pdf` for LaTeX and `.html`
  (Plotly) for the site. A function named `plot_*` only plots. The caller
  saves.
- **Numbers in prose** go in a generated `_output/stats.tex`:
  ```python
  def write_latex_macros(stats, path):
      """Write {name: value} as \\newcommand macros for the report."""
      lines = [f"\\newcommand{{\\{name}}}{{{value}}}" for name, value in stats.items()]
      path.write_text("\n".join(lines) + "\n")

  write_latex_macros({"SampleStart": "1990", "MeanSpread": f"{mean_spread:.2f}"},
                     OUTPUT_DIR / "stats.tex")
  ```
  ```latex
  \input{\PathToOutput/stats.tex}
  ... the average 10y--2y spread since \SampleStart{} was \MeanSpread{} percentage points.
  ```
  Macro names must be letters only (no digits or underscores).

## The LaTeX report
```latex
\newcommand*{\PathToAssets}{../assets}
\newcommand*{\PathToOutput}{../_output}
...
\begin{table}[htbp]
  \centering
  \caption{Summary statistics of GSW zero-coupon yields. Average yields rise
           with maturity over the sample.}   % a caption states what to learn
  \input{\PathToOutput/summary_table.tex}
\end{table}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.8\linewidth]{\PathToOutput/term_spread.png}
  \caption{The 10y--2y spread turned negative ahead of most recent recessions.}
\end{figure}
```
Rubric-level expectations (course final project):
- A single document that briefly describes the project and contains **every**
  table and chart the code produces.
- It summarizes successes, challenges and data sources at a high level.
- **No code snippets.** Notebooks and the site are where code is shown.
- **Every caption states what the reader should learn.**
- **Every statistic comes from code.**
- Compile with `latexmk -xelatex -halt-on-error -cd reports/report.tex` inside a
  doit task, after the tests pass.

## ChartBook catalog and site
`chartbook.toml` registers what the pipeline produces, so readers and other
pipelines can find it and trace it to raw sources:
```toml
[project]
id = "yield_curve"
name = "GSW Yield Curve Pipeline"
description = "Daily zero-coupon Treasury yields and term-spread diagnostics."
maintainer = "Your Name"
contributors = ["Your Name"]
build = """
doit
"""

[dataframes.yield_curve_tidy]
path = "./_data/yield_curve_tidy.parquet"
docs = "One row per (date, maturity). Zero-coupon yield in percent, continuously compounded. Source: Federal Reserve (GSW 2007), public."

[charts.term_spread]
path = "./_output/term_spread.html"
docs = "10y minus 2y zero-coupon yield."

[notebooks.01_data_tour]
description = "Tour of the cleaned yield curve and validation checks."
path = "_output/01_data_tour.ipynb"
```
- Manifest format v2 uses a single `[project]` table with de-prefixed fields
  (`name`, `path`, `tags`). Older v1 manifests used `[config]`, `[site]` and
  `[pipeline]` with prefixed fields such as `chart_name` and
  `path_to_parquet_data`. Match whatever version the installed `chartbook`
  expects (run `chartbook --help` and look at the docs). Field names are the part
  most likely to drift.
- For each dataframe, record its sources, providers, access type, license and
  how it is pulled. That governance metadata is what makes a catalog useful at a
  firm.
- `chartbook build -f` builds the site into `docs/`. Run it as a doit task
  after notebooks and tests. `chartbook browse` opens it locally.
- Downstream projects load registered data **by name, not by path**:
  `from chartbook import data; data.load(pipeline="scope/name", dataframe="x", format="pandas")`.

## GitHub Pages
- Serve from a branch's `docs/` folder, or deploy with an Actions workflow.
- Put a `.nojekyll` file at the root of the served folder. Without it, files
  and folders that start with `_` are dropped.
- A workflow that commits rebuilt outputs needs write permission (Settings → Actions → Workflow permissions).
- For a self-updating dashboard: a scheduled workflow (`on: schedule: - cron: ...`)
  pulls fresh data, runs `doit`, and publishes. Keep the test workflow separate
  from the publish workflow.

## Documentation of code
- Each module has a docstring stating its purpose. Public functions have
  docstrings with parameters, returns and an example (doctest) where useful.
- Sphinx (or ChartBook, which builds on it) generates reference pages from
  docstrings, so the docs live next to the code and never fall behind it.
