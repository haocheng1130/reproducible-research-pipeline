# Project Structure

## Why a fixed layout
These are the Cookiecutter Data Science take-aways that the course adopts:
- "Other people will thank you". "You will thank you."
- "Data is immutable (pull fresh when you can)."
- "Analysis is a DAG (build system)."
- "Build from the environment up" (use a virtual environment and start sparse).
- "Keep secrets out of version control. Use `.env` files."

The course template is `backofficedev/cookiecutter_chartbook`. Older repos use
`jmbejara/blank_project`, which is now deprecated. Scaffold a project with:

```bash
pip install cruft
cruft create https://github.com/backofficedev/cookiecutter_chartbook
# later, pull template updates into the project:
cruft diff      # preview what changed upstream
cruft update    # apply it
# in CI: `cruft check` exits non-zero when the template has updates
```

## Directory contract

| Path | Content | In git? | Can delete? |
|---|---|---|---|
| `src/` | All code: pulls, cleaning, analysis, outputs, notebooks (`*.ipynb.py`), tests | yes | no |
| `dodo.py` | Task DAG | yes | no |
| `_data/` | Everything pulled from external sources (Parquet preferred) | **no** | yes. `doit` re-pulls |
| `_output/` | Generated tables (`.tex`), charts (`.html`/`.png`), executed notebooks, logs | **no** (small outputs may optionally be tracked) | yes. `doit` regenerates |
| `data_manual/` | Data that **cannot** be re-pulled: hand-collected tables, one-off vendor files you may keep. Include a `README.md` describing provenance | yes (Git LFS if large) | **no** |
| `assets/` | Hand-drawn diagrams and logos. Anything not generated by code | yes | no |
| `reports/` | LaTeX sources (`.tex`, `.sty`, `.bib`). PDFs are build products | `.tex` yes, `*.pdf` no | PDFs yes |
| `docs_src/` | Markdown docs for dataframes, charts and site pages | yes | no |
| `docs/` | Built site (ChartBook/Sphinx) | usually no. Built in CI | yes |
| `.env.example` | Documented variables with dummy values | yes | no |
| `.env` | Real paths and secrets | **never** | - |
| `.github/workflows/` | CI | yes | no |

The test for where a file belongs: *if I delete it, can `doit` recreate it?*
If yes, it goes in `_data/` or `_output/` and is gitignored. If no, it goes in
`data_manual/` or `assets/` and is committed.

Two paths are configurable: `_data` and `_output` can live elsewhere, for
example a shared drive or HPC scratch, by setting `DATA_DIR` and `OUTPUT_DIR`
in `.env`. Code never assumes their location. It always asks `settings.config`.

## File naming inside `src/`
| Prefix | Responsibility | Examples from the course |
|---|---|---|
| `pull_` | Fetch from an external system (WRDS, API, web, Bloomberg). Contains `pull_*` **and** `load_*` functions | `pull_CRSP_Compustat.py`, `pull_fred.py`, `pull_SP500_constituents.py` |
| `load_` | (function prefix) read cached data from `_data/` | `load_compustat()`, `load_fred()` |
| `clean_` | Project-specific filters → tidy data | `clean_trace_local.py` |
| `calc_` | Analysis, replication and model logic | `calc_Fama_French_1993.py`, `calc_CRSP_indices.py` |
| `create_`/`chart_`/`table_` | Write exhibits to `_output/` | `chart_relative_repo_rates.py`, `example_table.py` |
| `NN_*.ipynb.py` | Jupytext notebook, numbered in reading order | `01_markowitz.ipynb.py` |
| `test_` | pytest module for the matching file | `test_port_opt.py`, `test_pull_fred.py` |
| `settings.py` | The only config module | |
| `misc_tools.py` | Small generic helpers (weighted averages, lags, date helpers) | |

Shared domain logic that several `calc_` files use gets its own module
(for example `shared_portfolio_sorts.py` in HW1). Do not copy and paste it.

## README skeleton
```markdown
# <Project name>

<One-paragraph description: what this produces and who uses it.>

## Charter
- Claim / target (one sentence):
- What existing work lacks:
- What this repo builds:
- Who would clone it and why:
- How success is verified (replication targets + validation checks):

## Quick start
    conda create -n <env> python=3.12      # or: uv sync / pixi install
    conda activate <env>
    pip install -r requirements.txt
    cp .env.example .env                   # then fill in credentials/paths
    doit                                   # pulls data, builds everything
    pytest                                 # or: doit test

## Data sources
| Dataset | Provider | Access | Pulled by | License/restrictions |

## Outputs
| Output | Produced by | Location |

## Repository map
| Path | Purpose |

## Extension / Update (if replicating a paper)
- Update: re-run exhibits on latest data. Did the result hold?
- Extension: what this adds beyond the paper (agreed scope).
```
